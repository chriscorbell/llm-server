# 2026-09-07 MTP depth 3 against depth 4

Status: concluded
Profile: A
Author: agent thread on mbp

## Hypothesis

The fourth speculative token is accepted about 25% of the time and only when the first three were also accepted, so dropping to three draft tokens should cost little accepted throughput, remove wasted draft and verification work per step, and return a small amount of KV capacity. Expected result: decode within a few percent of depth 4, possibly higher, with more KV tokens. No quality change is possible because target verification is exact.

## Configuration

One variable: `MTP_TOKENS=3` in `compose/.env` on the server, replacing `MTP_TOKENS=4`. Everything else unchanged: same image digest, `--dtype float16 --kv-cache-dtype auto`, 98,304 context, utilization 0.95, one sequence, 8,192 batched tokens, prefix caching on.

```bash
ssh vllm "sed -i 's/^MTP_TOKENS=4$/MTP_TOKENS=3/' ~/Code/llm-server/compose/.env && \
  cd ~/Code/llm-server/compose && docker compose --profile a-bf16kv down && \
  docker compose --profile a-bf16kv up -d"
```

Both arms measured the same evening, same harness, same corpus, one after the other:

```bash
for p in 512 8192 32768; do
  ./scripts/bench.py --base-url http://vllm:8000 --key "$KEY" --corpus code \
    --thinking --prompt-tokens $p --gen 256 -n 3 \
    --json eval/results/2026-09-07-mtp-depth/mtp<depth>-p$p.json
done
```

Concurrency 1, cold prefix each repetition, thinking on, temperature 1.0, top_p 0.95, top_k 20, 256 generated tokens, medians of three after a discarded warmup. Acceptance is the Prometheus counter delta across each command, including its warmup.

Baseline for comparison: the depth 4 arm below, measured minutes before the change. Earlier per-position figures are in [decode speed and MTP acceptance](2026-09-07-decode-speed-and-mtp-acceptance.md).

TTFT and prefill are unchanged at every size, as expected, because draft depth only affects decode steps.

## What happened

The restart was clean. Health returned after about 225 seconds. `scripts/smoke.sh` passed all five checks against the depth 3 server: models, plain text, reasoning present, tool call, vision.

The first three per-position rates barely moved between arms (0.703/0.484/0.326 against 0.716/0.494/0.358), which is what exact verification predicts: the draft head's guesses for positions one to three are the same guesses, the server just stops asking for a fourth. Mean acceptance length fell from 2.75 to 2.57 tokens per step, so depth 3 generates about 0.18 fewer tokens per step, and decode did not fall, which means each step got cheaper by at least that share. The per-position rate for position four at depth 4 was 0.235 in this run, close to the 0.253 measured earlier.

The earlier decode-speed experiment recorded 105,640 KV tokens with prefix caching off and 103,326 with it on, at depth 4. The depth 3 figure matches the former exactly. That is a coincidence of the allocator's rounding, not evidence that prefix caching is off; the compose command still passes `--enable-prefix-caching` and warm requests during the validation run continued to return in under a second.

The `gpu-health.sh` capture before the restart showed `xe` fault lines timestamped 23:30 UTC, more than two hours before this experiment, from the earlier watchdog episode. No new GPU faults appeared during either arm.

## Outcome

Confirmed. Depth 3 is never slower than depth 4 across three context sizes at six repetitions each, is 3 to 4 tok/s faster at short context, and returns 2,314 KV tokens. Quality cannot change because target verification is exact and vLLM's rejection sampler preserves the sampling distribution. There is no measured reason to keep depth 4.

Depth 2 was not tested. Position three still accepts 36% of the time, so dropping it would remove real accepted tokens; that is a separate one-variable experiment if anyone wants it.

## Consequences

`MTP_TOKENS=3` is now the value in `compose/.env` on the server and in `compose/.env.example`. The server is running depth 3. `STATUS.md` records the new configuration, the new KV capacity and a Finding pointing here. Raw JSON and engine metric lines are in `eval/results/2026-09-07-mtp-depth/` on mbp, which is gitignored; the tables above carry every number used.
